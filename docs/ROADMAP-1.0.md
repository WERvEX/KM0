# KM0 正式版（1.0）规划

状态：规划中（2026-10）。本文档随实现推进更新；每完成一个阶段，把定稿的设计并入 [DESIGN.md](DESIGN.md)。

## 目标

0.1 有三个限制：

- 档位只看任务、不看模型。同样是 T2，在 Claude Code 里可能是 Sonnet，在 Pi 里可能是能力差很多的模型，规则却一样处理。
- 只能用内置的 7 个 Agent，每个 Agent 每档一个模型，价格全靠手填，只有按 token 计费一种。
- 执行在 KM0 之外：要在命令行跑 KM0 Runner，再把运行文件夹导入 KM0。

正式版的做法：

- **评估**：每个模型在每种能力上有一个能力值的概率分布。先验来自公开榜单，后验用用户自己的验收结果修正（贝叶斯更新）。本期重点优化先验；后验的更新逻辑实现并用合成数据测试，不做真实数据的评测，因为每个用户配置的模型不同，得不出通用结论。
- **分发**：在用户实际可用的（Agent, 模型）组合里，按预计通过率和期望成本选择。用户在“激进（节约成本）”到“保守（保证质量）”之间选一档。
- **自定义**：用户可以加入自己的模型和 Agent，计费方式有多种可选。
- **执行**：在 KM0 里一键启动 KM0 Runner 并展示进度，跑完自动导入和验收。也可以配置自定义的执行路径或启动方式，但这些方式暂不做兼容性验证。
- **成品界面**：所有确认、提示、错误和选择都用 KM0 自己的组件，不出现系统或浏览器的弹窗，并有自动化校验。

不做：

- 不在应用里实时抓取榜单，不上传任何用户数据。
- 不把 Runner 产出的分支合并进用户的仓库。
- 自定义执行方式只保证能启动、能显示输出、能导入符合格式的结果。

## 1. 模型注册表与自定义 Agent

### 表结构

0.1 里 KM0 自用的模型（`llm_profiles`）和交给 Agent 的模型目录（`model_catalog`，Agent × 档位）是两套。正式版合成一套：

| 表 | 内容 |
| --- | --- |
| `providers` | 名称、接口类型（Anthropic / OpenAI 兼容）、地址、密钥（加密）、计费方式 |
| `models` | 所属 provider、模型 ID、规范 ID（对应榜单注册表）、上下文窗口、价格、结构化输出方式（KM0 自己调用时用） |
| `agents` | 字符串 ID、预设或自定义、启用、偏好顺序、项目说明文件、启动命令模板、能接的接口类型、擅长的能力 |
| `agent_models` | 某个 Agent 可以用哪些模型 |

KM0 的路由模型和规划模型从 `models` 里选。迁移会保留 0.1 的全部模型和价格；原来的“Agent × 档位”分配变成这些模型的初始档位标签（见第 3 节），用户可以改。迁移前自动备份数据库文件。

### 计费方式

按 provider 设置，单个模型可以覆盖：

| 方式 | 需要填写 | 成本怎么算 |
| --- | --- | --- |
| 按 token | 输入、输出、缓存读写单价（能从注册表自动填） | 估算 token × 单价 |
| 中转倍率 | 官方价的倍率，或充值汇率 | 官方价 × 倍率 |
| 订阅 | 月费；额度（每 5 小时、每周的请求数或 token 数，选填） | 额度内边际成本按 0 计，但按额度占用加一个影子价格，避免小任务把额度用光；额度用完时按用户设定退回按 token 计费或不可用 |
| 免费 / 本地模型 | 可选的速率上限 | 0 |

成本照旧显示为区间并标注“估算”。订阅显示为“约占用额度 x%”。

### 自定义 Agent

`AgentId` 从固定的 7 个枚举改成字符串 ID，内置的 7 个变成预设，可以复制成自定义 Agent 再修改。自定义 Agent 填写：

- 名称；
- 项目说明文件：`AGENTS.md`、`CLAUDE.md`、自定义路径或无；
- 启动命令模板，占位符 `{model}`、`{prompt}`、`{task_file}`；
- 能接的接口类型；
- 本家模型：这个 Agent 是哪家模型厂商的官方工具（可以不填）；
- 擅长的能力。

### 本家匹配

模型厂商自己的 Agent 通常针对自家模型调过提示词和工具，同一个模型放在本家 Agent 里表现更好。注册表维护一张“厂商 → 本家 Agent”的表，KM0 用规则把用户配置的模型和 Agent 对上：

| 厂商（模型系列） | 本家 Agent |
| --- | --- |
| Anthropic（Claude：Opus、Sonnet、Haiku） | Claude Code |
| OpenAI（GPT、o 系列、Codex 模型） | Codex |
| DeepSeek | DSH |
| 智谱（GLM） | ZCode |
| Cursor 自己的模型 | Cursor |
| 其他厂商（Qwen、Kimi、MiMo、Gemini 等） | 没有内置的本家 Agent，可以自定义添加；Pi 和通用格式不绑定厂商 |

匹配的步骤：

1. 用户填的模型 ID 按别名表对应到规范 ID，从而知道厂商；对不上时让用户手动选厂商。
2. 内置 Agent 的本家厂商来自注册表，自定义 Agent 用用户填写的“本家模型”。
3. 同一个模型有多个 Agent 可用时，本家 Agent 优先：先验里给一个正的 Agent 修正值（有榜单的 Agent + 模型数据时以数据为准，见第 2 节），预计通过率接近时也优先选本家 Agent。
4. 用户可以对单个组合关掉本家优先，或者改用别的 Agent。

规则匹配的结果在“设置 → Agent”里列出来，例如“Opus 5.5 → Claude Code（本家）”，用户维护的信息和注册表维护的信息不一致时（例如用户把 GPT 模型配给了 Claude Code），列出提示但不阻止。

交接包对自定义 Agent 使用通用适配器，启动命令按模板生成。改动面涉及 shared 的 schema、数据库迁移、交接适配器、路由和快照测试。

## 2. 榜单数据与先验

### 数据来源

下表是候选来源。R2 的第一步是逐个核实获取方式、更新频率和许可；不允许抓取的来源改为人工录入，或者放弃。

| 榜单 | 测什么 | 对应能力 | 备注 |
| --- | --- | --- | --- |
| SWE-bench Verified / Pro | 真实仓库的 issue 修复 | 后端、调试 | Verified 有按人工耗时标注的难度分档，可用来锚定任务难度（见下文）；分数接近饱和，有污染风险，需要降权 |
| Multi-SWE-bench、SWE-bench Multilingual | 非 Python 仓库的 issue 修复 | 后端、调试 | 补充语言覆盖 |
| Terminal-Bench | 终端里的综合任务，按 Agent + 模型组合排名 | 部署与配置；Agent 修正项 | 少有的能区分 Agent 本身影响的数据 |
| SWE-bench 的 bash-only 与各 Agent 提交 | 同一批题目上，裸模型和各家 Agent 的成绩 | Agent 修正项 | 同一模型在不同 Agent 下的差值就是 Agent 修正的直接证据 |
| Aider Polyglot | 多语言代码编辑 | 后端、前端 | |
| WebDev Arena | 网页应用生成，人工两两对比 | 前端 | Elo 分 |
| LiveCodeBench | 按时间滚动的算法题 | 推理（需要设计决策的任务） | 滚动出题，污染较少 |
| OpenRouter 模型列表、厂商价格页 | 价格、上下文窗口、发布时间 | — | 用来自动填价格和上下文 |

能力维度沿用现有的 6 项（前端、后端、调试、测试、文档、部署与配置）。测试和文档几乎没有专门的榜单，由总体能力推出，不确定度更大。

### 数据管道

- **位置**：KM0 仓库的 `registry/` 目录，存放抓取脚本、别名表、人工补录数据和生成的快照。CI 每周运行一次，也可以手动触发。
- **步骤**：抓取 → 保存原始快照（可复现） → 名称对齐 → 归一化 → 补全缺失 → 拟合先验 → 生成 `model-registry.json` → 发布。
- **发布**：`model-registry.json` 带 schema 版本、数据日期和每个数值的来源，发布到 GitHub Pages 的 `/registry/` 路径（和网页调试版共用 `gh-pages` 分支，互不覆盖），同时打进安装包作为内置快照。
- **应用内更新**：设置里可以检查更新或手动导入文件；离线时用内置快照。只下载，不上传。
- **名称对齐**：每个模型有规范 ID（厂商 / 模型 / 版本），另有别名表记录各榜单的写法、中转常用的写法和日期后缀。对不上的新名字由 CI 列出，人工确认后写进别名表，不做自动的模糊合并。用户在 KM0 里填的模型 ID 也按别名表对应到规范 ID，对不上时让用户手动选。
- **归一化**：通过率类分数转成 logit，Elo 类分数本身就是 logistic 尺度；再用全部“模型 × 榜单”数据一起拟合，把每个榜单线性映射到同一条能力刻度上。
- **补全缺失**：模型 × 榜单矩阵里缺失很多。榜单之间相关性强，用低秩分解补全，并给出补全值的不确定度。完全没有榜单数据的模型，按同家族、同价位的模型给先验，方差加大，并标注“无榜单数据”。用户也可以指定“和某个模型相当”。
- **时效与污染**：分数按数据日期衰减权重；同一模型多次测量时以新的为准。已知饱和或有污染风险的榜单降权。权重都写在可审阅的配置文件里。

### 先验模型

- **能力**：模型 m 在能力 c 上的能力值 θ ~ N(μ, σ²)。μ 来自上面的拟合；σ 反映覆盖程度：有几个榜单、补全的不确定度、数据新旧。
- **Agent 修正**：同一个模型在不同 Agent 里表现不同。有 Agent + 模型组合数据（例如 Terminal-Bench、SWE-bench 上各 Agent 的提交）时，按数据估计修正值 δ；没有数据时，本家 Agent 取一个正的先验均值（初值从有数据的本家组合里估计），其他 Agent 取 0，方差都加大。自定义 Agent 按用户填写的本家模型套用同样的规则。
- **任务难度**：沿用现有的特征打分（影响范围、需求模糊度、推理难度等），把分数映射成同一刻度上的难度 d。刻度用 SWE-bench Verified 的难度分档锚定：把 KM0 的特征组合对应到“15 分钟以内 / 15 分钟–1 小时 / 1–4 小时 / 4 小时以上”，再用各模型在各分档上的通过率拟合（需要逐题结果，R2 核实能否取得）。现有的硬规则改为难度的上下限，以及风险任务的能力下限。
- **通过概率**：P(通过) = σ(a · (θ + δ − d))。
- **后验**：每条验收结论（KM0 的判定、Runner 的升档记录、手动“记一次失败”）对相应的 θ 做一次贝叶斯更新，用正态近似，纯 TypeScript 实现，不加依赖。本期只用合成数据测试。界面显示“本地记录 n 次”，用户可以清除。用户手动修改能力值，按一次强观测处理。
- Runner 校准出的 `routing-rules.json` 仍然可以导入，用来替换难度刻度。

### 先验的评估与调参

先验的评估只用公开数据，不用用户数据：

- **留一榜单**：用其余榜单预测被留出的那个，看误差，以及区间覆盖率（例如 90% 区间是否覆盖约 90% 的真实值）。
- **时间切分**：只用某个日期之前的数据，预测之后发布的模型。
- **排序一致性**：预测的能力排序和各榜单排序的 Kendall τ。

每次运行数据管道都生成一份评估报告（Markdown，提交进仓库），指标变差时 CI 标红。要调的参数有：榜单权重、时效衰减速度、补全的秩、能力维度与榜单的对应权重。

## 3. 分发策略

### 候选与硬约束

每个任务的候选是“已启用的 Agent × 它能用的模型”，先按硬约束过滤：

- 上下文窗口不小于任务估算的上下文量；
- Agent 能接这个模型的接口类型；
- 订阅额度已经用完的排除（填了额度时才判断）；
- 有风险类型的任务需要达到能力下限。

### 选择

对每个候选算出首次通过概率（带不确定度）和一次运行的成本，再沿升级链算期望总成本：首次成本 + (1 − p₁) × (下一级的期望成本) + …。

策略分五档，项目级设置，单个任务可以覆盖：

| 档 | 名称 | 首次通过率目标 | 能力值取法 |
| --- | --- | --- | --- |
| 1 | 激进 | ≥ 50% | 均值 |
| 2 | 偏省 | ≥ 60% | 均值 |
| 3 | 平衡（默认） | ≥ 70% | 35% 分位 |
| 4 | 偏稳 | ≥ 80% | 25% 分位 |
| 5 | 保守 | ≥ 90% | 10% 分位 |

数字是初值，写在配置里，可以调整。

- 在达到目标的候选里选期望总成本最低的。没有候选能达到目标时，选通过率最高的，并标注“没有达到目标通过率的组合”。
- 越保守的档位，能力取越低的分位，所以不确定度大的模型（例如没有榜单数据的）越少被选中；激进档用均值，愿意给便宜但没把握的模型机会。
- 有风险类型的任务至少按“偏稳”处理。
- 预算上限：可以设项目总预算。超出时提示哪些任务降档后能放进预算。
- 本家优先：同一个模型的多个 Agent 之间，预计通过率差在 5 个百分点以内时选本家 Agent（见第 1 节）。
- 升级链：失败后换到能力更高的下一个组合，同一个 Agent 优先。交给 Runner 的阶梯也由升级链生成。
- T1/T2/T3 保留为显示用的标签：按模型能力在用户自己的模型里的位置自动分档，用户可以改某个模型的档位标签。

### 理由与覆盖

每个任务显示：

- 预计通过率（区间）、期望成本，以及和“全部用最强组合”相比的节省；
- 为什么没选更便宜的，例如“模型 X 预计通过率 48%，低于目标 70%”；
- 数据来源：用了哪些榜单及数据日期、本地记录了几次。

Agent、模型和档位都可以逐个任务手动覆盖，也可以恢复成策略的结果。

### 需要单测的性质

- 单调性：档位越保守，选出组合的预计通过率不降、期望成本不降。
- 条件相同时选更便宜的组合。
- 风险任务的能力下限生效。
- 没有候选时走退化路径。
- 每一种计费方式下的成本计算。

## 4. 执行

### 执行方式（设置 → 执行）

**默认：KM0 Runner**

- Runner 路径：自动检测 PATH 里的 `km0-runner`，或手填可执行文件，或 `python -m km0_runner`。显示版本，低于最低版本时提示升级。
- pi：检测是否安装，以及版本是否为 Runner 锁定的版本。
- 运行目录：默认是应用数据目录下的 `runs/`，可以改。
- Runner 配置默认由 KM0 根据模型注册表生成：阶梯取自分发的升级链，pi 的 `models.json` 取自 providers。密钥只通过环境变量传给子进程，不写进文件。也可以改用自己的 `runner.yaml`。

**自定义执行方式（标注“未验证”）**

- 填命令模板、工作目录和环境变量，占位符有 `{package}`（交接包目录）、`{repo}`、`{run_dir}`、`{tasks}`。
- KM0 只负责启动、显示输出和停止。结束后，如果 `{run_dir}` 里有 Runner 格式的结果就导入，否则提示手动导入。

网页调试版不能启动本地进程，执行入口显示为不可用，并说明原因。

### 一键执行流程

1. 在交接面板点“执行”。
2. 预检：仓库是 git 仓库、Runner 和 pi 可用、每个任务都有可用的模型、没有超出预算。预检结果在面板里逐项列出，不通过的项给出去哪里修改。
3. 写出交接包，启动 Runner，打开执行面板。
4. 结束后自动导入运行结果，并开始验收。
5. 未通过的任务可以“从高一档重做”（对应 Runner 的 `--reuse`）。

### 进度与停止（需要改 KM0 Runner）

- Runner 在运行目录里写 `progress.jsonl`，KM0 跟随读取；KM0 重启后也能接着读。事件有：`run_started`、`task_started`、`attempt_started`（档位、模型）、`escalation`、`test_result`、`merge_resolution`、`task_finished`（状态、成本）、`run_finished`。
- 优雅停止：收到停止请求时（POSIX 用 SIGTERM，Windows 用停止文件），停下 pi，写出部分报告，把任务标记为 `cancelled`，并清理 worktree。
- 执行面板显示：
  - 每个任务的状态：等待、执行中、通过、升档、失败、阻塞、已取消；
  - 当前档位和模型、累计成本和预算、升档记录、最近几行日志；
  - 停止按钮。
- 运行结束用应用内提示告知，不发系统通知。
- 新增 `runs` 表：run_id、项目、执行方式、状态、起止时间、运行目录、成本。

## 5. 界面规范与成品校验

### 规则

- 不使用 `alert`、`confirm`、`prompt`、Electron 的 `dialog.showMessageBox` / `showErrorBox`，也不使用系统通知。确认、提示、错误、进度全部用 KM0 的组件：确认对话框、应用内提示条、行内错误、空状态、加载状态。
- 选择文件夹：桌面版改为应用内的文件夹浏览器（主进程只读列出目录，也可以直接输入路径），不再弹出系统的选择框。网页调试版没有别的办法访问本地文件夹，只能用浏览器自带的文件夹选择框，这是唯一的例外。
- 主进程里未捕获的异常不能弹出 Electron 默认的错误框：捕获后写日志，并在界面里显示错误页。
- 退出时如果还有执行没结束，用应用内的确认对话框询问。
- 自动更新的下载进度和安装提示都显示在应用内。
- 在 `components/ui` 里补齐确认框、提示条、侧滑面板和文件浏览器（R0 已完成）；下拉框、表格、进度条、标签和空状态在 R4、R5 用到时加入。功能代码不直接写带样式的原生控件。
- 保存和导入文件同样不弹系统对话框：桌面版在 KM0 自己的文件浏览器里选文件夹和文件名，已有同名文件时在同一个对话框里确认覆盖，保存后用提示条告知路径并可以“在文件夹中显示”。

### 校验

| 检查 | 方式 | 何时运行 |
| --- | --- | --- |
| 源码里没有原生弹窗 | CI 脚本搜索 `alert(`、`confirm(`、`prompt(`、`dialog.show*`、`new Notification` 等；允许清单只有网页版的文件夹选择 | 每次推送 |
| 运行时没有弹窗 | e2e 监听页面的 `dialog` 事件，一出现就判失败；测试模式下把 Electron 的 `dialog` 换成一调用就抛错的桩 | e2e |
| 截图集 | 关键界面（各讨论阶段、文档页、路由表、交接、设置各页、文件浏览器、确认框；R5 起加上执行面板）在 1280×800 和 1024×700 两种窗口、中英文、浅色和深色下截图，生成 `test-results/ui/index.html` 供人工确认，CI 作为构建产物上传 | e2e |
| 布局 | 窗口和各栏不横向滚动；文字不被截断（除非带省略号）、不跑出屏幕；按钮和标签页的文字不折行；没有只差几像素的多余滚动条 | e2e |
| 可访问性 | axe-core（WCAG 2.1 AA）没有 serious 或 critical 问题，包括颜色对比度；对话框能只用键盘操作，打开时焦点进入、关闭后回到打开它的按钮 | e2e |

不做像素级的基线比对：同一界面在不同机器上用的中文字体不同（这个仓库的开发容器和 CI 的 Ubuntu 就不同），像素比对会误报。上面的布局检查和可访问性检查与字体无关，截图集留给人工确认。
| 人工确认 | 每个带界面的阶段完成后暂停，把截图交给用户确认 | 阶段验收 |

## 6. 评测与发布

- **离线评测集**：把已有的校准请求（带隐藏测试）整理成固定的评测集，模型回答用文件桥录下来，回放时不需要 API Key。检查两件事：拆解是否保留了所有验收条件；评审结论和隐藏测试的结果是否一致。改了 prompt 后要重新录制，这一步手动触发，不进 CI。
- **签名与公证**：需要 Windows 代码签名证书和 Apple Developer 账号，由仓库所有者提供，放在 CI 的密钥里。没有时照常发布未签名版，并在发布说明里写清。
- **自动更新**：electron-updater 走 GitHub Releases，界面都在应用内。
- **升级测试**：用 0.1.0 的数据库文件跑全部迁移，检查数据完整。
- **文档**：更新 DESIGN.md、README 和发布说明。

## 分阶段实施计划

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| R0 界面规范 | 第 5 节的规则和组件；替换现有的文件夹选择框、文件导入和下载；主进程异常处理；CI 检查、布局与可访问性检查、截图集 | CI 能拦下原生弹窗；e2e 中出现弹窗即失败；全部界面通过布局与可访问性检查；**完成后暂停，请用户确认组件风格** |
| R1 模型与 Agent | 合并后的表结构与迁移；provider 与计费方式；自定义 Agent；`AgentId` 改为字符串；本家匹配规则；设置页 | 0.1.0 数据库的迁移测试；自定义 Agent 出现在路由和交接包里（快照测试）；每种计费方式的成本单测；本家匹配的规则单测 |
| R2 榜单管道 | 核实来源；抓取、对齐、归一化、补全；`model-registry.json` 的发布与内置；应用内更新与导入 | 用固定的原始快照能复现生成结果；对不上的名字由 CI 列出；每个模型都有先验并标注覆盖情况 |
| R3 先验与后验 | 能力模型、Agent 修正、难度刻度、通过概率；后验更新；先验评估报告与调参 | 合成数据下后验收敛到真实值；留一榜单的 90% 区间覆盖率在 80%–95% 之间；评估报告提交进仓库 |
| R4 分发策略 | 五个策略档位、期望成本、硬约束、预算、升级链、理由；路由表界面 | 单调性和边界单测；e2e 中切换档位后路由按预期变化；**完成后暂停，请用户确认路由表和理由的呈现** |
| R5 执行 | Runner 的进度文件与优雅停止（KM0-runner 仓库）；执行设置；Runner 配置生成；预检；执行面板；自动导入与验收 | 用假 pi 驱动 Runner，在 e2e 中跑完、停止、导入、验收；自定义执行方式能启动并显示输出 |
| R6 评测与发布 | 离线评测集；签名与公证；自动更新；升级测试；文档 | 全量测试通过；三平台安装包；**最终界面验收** |

顺序：R0 → R1 → R2 和 R3（可以并行） → R4 → R5 → R6。R5 里 Runner 一侧的改动在 R1 完成后就可以开始。

## 风险

| 风险 | 应对 |
| --- | --- |
| 榜单不允许抓取，或格式经常变 | 每个来源一个独立的抓取器，失败只跳过该来源；允许人工录入 |
| 模型名字对不上 | 规范 ID + 别名表 + CI 列出未对齐的名字；不做自动模糊合并 |
| 榜单任务和用户任务差别大，先验偏离真实表现 | 不确定度直接进入选择（保守档用低分位）；后验修正；用户可以直接改能力值 |
| 各家订阅额度规则不同且常变 | 额度只是可选输入，没填时按“不限”处理并提示 |
| Runner 在 Windows 上未验证 | R5 先在三平台 CI 上跑 Runner 的测试；跑不通时，Windows 上提示改用 WSL |
| 迁移破坏老用户的数据 | 迁移前自动备份数据库文件；升级测试 |
| 签名证书需要付费账号 | 由仓库所有者提供；没有时发布未签名版并写清 |
